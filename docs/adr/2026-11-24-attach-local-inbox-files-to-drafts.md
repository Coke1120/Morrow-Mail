# Attach stored Inbox files from a resumed draft

An ordinary saved draft can attach files from its own account’s Inbox. The picker shows the draft’s To, Cc and Bcc together with the source sender, subject, date, file name and size. Opening the picker, checking a file and cancelling leave both messages untouched. Only **Add selected files** adds the checked files to the open editor. **Save draft** persists the change.

The picker uses the existing cached-list and draft-preparation calls from a Compose window. In strict-local mode the host reads a bounded page of Inbox headers and file metadata. A file qualifies through its existing local blob or an unexpired, completed attachment transfer for the same account and exact message snapshot. Looking up a transfer never starts or joins a download, extends its lifetime or changes eviction order. An expired attachment can be downloaded again from its reader before reopening the picker.

Each displayed choice carries a host-generated proof bound to the editor, review, recipients, saved draft revision, account incarnation, source message and part. For persistent files the store incarnation, SQLite rowid, length and SQLite data version bind the selection to the same open database and exclude an intervening commit from another connection. The byte read checks those values in the same SELECT. Production blob writers allocate fresh IDs. A completed transfer instead has its own per-fill generation. Checking a file binds a keyed digest of its bytes to that choice. Confirmation verifies the digest against the actual bytes returned to the editor. This also detects different content if SQLite reuses a rowid. Listing a page reads no file bodies. Selection and confirmation are bounded by the existing 25 MiB outgoing attachment limit.

The editor checks its current recipients, session and saved draft before staging bytes through the existing local upload path. It adds the whole verified selection together and retains the PDF bytes for an immediate preview. Closing or cancelling the picker retires the request. A stale reply cannot update either draft. Staging follows the existing attachment lifecycle, including the possibility of unreferenced staged blobs when work is interrupted. The reader and the provider have no new channel or permission.
