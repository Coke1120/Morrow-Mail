# Mail identity, external flags and discovery ownership

Every UID-based write selects its source mailbox under an IMAP lock and compares the selected UIDVALIDITY with the cached source identity before issuing a command. This includes flags, moves, permanent deletes, Undo, local inbox rules and draft cleanup/replacement. Missing or changed validity refuses the write and asks for Sync. A known refusal rolls back the optimistic action rather than leaving an unknown receipt; it never retries a different message automatically. A refused draft discard keeps the local text, and a refused replacement saves locally with a Sync warning. Cleanup after an accepted SMTP send remains best effort so it cannot imply that the accepted message should be resent.

A completed folder reconciles one page of at most 200 cached UIDs with a flags-only FETCH, under the same selection lock as its existing live-UID reconciliation. The page uses an index on account, path, validity and UID. It starts at the newest UIDs, rotates toward older UIDs on successive passes, then wraps. The cursor is session state, not a journal write. Large folders can need multiple passes for all external flag changes to appear. Unchanged flags create no journal frame. Pending and unknown local actions protect only their affected read/star field; a pending/unknown move protects the row. A later completed flag action releases an older unknown projection.

Each manually edited server (IMAP or SMTP, including its port and TLS checkbox) opts that server out of discovery for the current dialog. The other server may still be discovered. Changing the address clears automatically filled endpoints immediately, including when discovery returns nothing; a partial result clears its absent half. Selecting a preset or reopening the dialog resets those edits. Reconnecting a saved Custom account treats both saved endpoints as explicit. Pending results cannot populate a reopened dialog, and changing the address/preset while Connect awaits discovery cancels that submission for review.

`scripts/check-mail-review-regressions.js`, included in `npm run check`, uses fake IMAP clients, temporary SQLite and form fixtures. It covers validity changes before every UID helper, action rollback/Undo/drafts, 450-message flag rotation and counts, unchanged-write budgets, optimistic field protection and discovery ownership/races. It does not contact providers or send mail.
