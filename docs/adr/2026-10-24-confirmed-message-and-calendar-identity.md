# Confirm identity before dependent operations

An optimistic move changes a message's displayed folder before IMAP returns its destination UID. That projected folder and the old UID are not a server identity. A message with an accepted or publishing move, delete or Undo refuses further writes and remote body/attachment reads until the structural operation settles. The refusal returns the current projection so the renderer can undo a rejected optimistic flag change. The user can retry after confirmation, using the confirmed destination UID and UIDVALIDITY.

Structural confirmations are never superseded by a newer flag action. Only read actions supersede other read actions, and star actions supersede other star actions. Failure rollback restores only the fields that the failed action projected. A permanently deleted message must actually be in the cached Trash folder; a stale Trash selection cannot delete an Inbox message. An Undo ticket is consumed after confirmed completion or an uncertain remote outcome. A definitely unissued Undo retains its ticket and exposes it in the settlement receipt for retry.

An interrupted or otherwise uncertain structural operation is not automatically replayed, and dependent operations remain refused on that projected row. Refresh the source and destination folders and select a fresh confirmed server copy. Accepted jobs written by older versions have no proof that their stored source was confirmed; on upgrade they settle as unknown without issuing a command. New accepted jobs record that they passed this barrier and retain normal restart processing. This deliberately favors a recoverable refusal over guessing which message a historical UID now identifies.

Full-body FETCH and attachment download compare the cached UIDVALIDITY with the selected mailbox while holding its IMAP lock, before requesting content. After an in-flight body read, the engine also checks that the cached identity is unchanged and has no unsettled structural action before storing the result. A mismatch returns a Sync/reopen error without replacing cached sender, subject or body information. Existing cached content can still be displayed without contacting the server.

An existing calendar event is edited and deleted using the account, calendar and event ID captured when its editor opened. The calendar picker is disabled for edits; creation retains it. Changing an event's calendar requires a separate supported move operation, which this dialog does not provide. Duplicate submissions are refused while a write is pending, and an older response cannot close a newly opened editor or mutate another account's view.

`scripts/check-confirmed-identity.js`, included in `npm run check`, covers pending move/delete and Undo, retry, unknown outcomes, legacy/restarted jobs, flag and structural rollback, body/attachment generation checks, an in-flight body/move race, and calendar identity/account/editor races with synthetic fixtures. The native Electron page-navigation fixture also verifies that programmatic picker changes cannot retarget an existing event.
