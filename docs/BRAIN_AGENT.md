# Brain skills and Agent triage

Morrow Mail uses the mailbox cache and the saved API/custom endpoint or ChatGPT account. Before any AI transfer, review **AI data permission** in Settings → AI or Morrow Mail → AI Setup and explicitly approve the disclosed destination/data use. Existing configurations start blocked. Automatic profile refresh, page-open triage, compose-open reply suggestions and scheduled skills require a separate background opt-in. Cancel / revoke stops queued and active AI requests; it cannot recall data already delivered. [Data categories, local/remote behavior and permission management](AI_DATA_USE.md). Errors never switch billing paths. The host has no sample mailbox.

## Skills

Home starts with the catalog installed. Library skills are the ones you removed. Install and remove persist in `agent.json` under the AI config directory (the same Electron userData directory as `ai.json` and `brain.json`).

Custom skills are ones you write. **New skill** on Brain → Skills, and on Agent → Skills, asks for a name, a short description, and an instruction. Optional switches add calendar context, focus on one person, or filing proposals. Save calls `emailBrain:saveCustomSkill` and puts the skill on Home. The same dialog edits it. Delete calls `emailBrain:deleteCustomSkill` and removes that definition, its schedule, and its home row. A deleted custom skill does not return to the library. Removing a catalog skill still only uninstalls it (`emailBrain:removeSkill`) and puts it back in the library.

Custom skill ids are `user:` plus a UUID. Catalog ids do not use that prefix. A catalog update does not overwrite a `user:` skill's id or instruction. Definitions live in `custom-skills.json` next to `agent.json`, only under userData. They are not stored in the app install, `resources/`, or `app.asar`. Reading a damaged file leaves it in place. Morrow does not replace it with an empty list, and it does not drop `user:` ids it does not recognize when it rewrites `agent.json`.

Packaged paths:

- Windows (NSIS and portable): `%APPDATA%\Morrow Mail\custom-skills.json`
- macOS: `~/Library/Application Support/Morrow Mail/custom-skills.json`
- Linux: `~/.config/Morrow Mail/custom-skills.json`

`app.setName("Morrow Mail")` selects that folder. NSIS does not set `deleteAppDataOnUninstall`. The macOS in-app update replaces the application bundle and leaves userData in place. Replacing a portable exe leaves the same userData directory in place. The first launch after an update reads the existing file.

Limits are 40 custom skills, a name of 80 characters, a description of 240, and a required instruction of up to 4000 characters. An empty instruction is rejected.

A custom skill runs with `emailBrain:runSkill`, the same path as a catalog skill. No API key or no mailbox returns `accepted: false`. Nothing is sent. With the switches off, the run sees recent inbox mail only. The calendar switch adds upcoming events when a calendar grant exists, and otherwise the run says it used mail only. The person switch needs an open message or a contact email, including on a schedule. The filing switch proposes folder or label moves and waits for Confirm, the same as Organize Inbox. With that switch off, move proposals are dropped. Schedule, pause, resume, and run match catalog skills.

| Skill | What it uses |
| --- | --- |
| Morning Brief | Recent inbox mail |
| Catch Me Up | Recent inbox mail |
| Organize Inbox | Recent inbox mail. Proposes a label or folder move |
| Plan My Week | Inbox mail, plus `calendar:list` when a calendar grant exists. Otherwise a mail-only plan |
| Newsletter Digest | Inbox mail that looks like newsletters or bulk mail |
| Brief This Person | A selected message in the local cache, or a contact email you pass in |
| Meeting Prep | Calendar events and related mail when a calendar grant exists. Otherwise mail only |

Home skills start as `runMode: on_demand` with `schedule: disabled`. Auto-execute stays off. An installed skill can save an interval from 1 to 10080 minutes, or a five-field cron schedule (`emailBrain:setSkillSchedule`). Edit writes that same schedule again. Pause keeps the row and does not fire. Delete (`emailBrain:deleteSkillSchedule`) returns the skill to on demand. Removing a skill deletes its schedule. Brief This Person stores a contact email on the schedule. While Morrow Mail is open, the host timer queues a due skill with `setImmediate` and returns. The window does not wait on the model. A run that was missed while the app was closed fires once, then waits for the next slot. The result lands in run history and `emailBrain:scheduleFired`. A manual run still calls the model only when you ask. Drafts open in a compose window. Send stays on the compose button.

Organize Inbox does not move mail until Confirm. Confirm uses Gmail labels or an Outlook folder when that organize grant exists, or an IMAP folder with the same name. No grant and no matching folder leaves the proposal pending. Dismiss drops it. Nothing is sent.

No API key returns `accepted: false` with the AI Setup error. No connected mailbox returns `accepted: false`. The host has no sample mailbox to read.

## Agent

Agent opens from the leftmost rail, in the same strip as Mail, Calendar, and Brain. It replaces the mail shell with the full Agent page: a greeting, category todo stacks, skill chips, Manage Skills, and a composer that says Ask Morrow Mail. On Conversation the transcript scrolls and the composer stays pinned at the bottom of that pane. The folder column and message list are the Mail page. Home todos come from `nativeAgent:home:todosCached`. Opening Agent paints that cache, then runs `nativeAgent:triage` when the cache is stale. Saving Brain categories calls `nativeAgent:home:refreshTaxonomy` so the stacks follow the new order. Reply, Reply All, and Mark as read show on a todo that has a message. Reply and Reply All open compose in a new window. A successful Reply or Reply All completes only the Needs You todo recorded when that reply starts; forward, a new message, a draft, a canceled compose, a failed send, and a queued or scheduled send leave it open until that send succeeds. Mark as read uses the same mark-read path as the message list and leaves the todo open unless Settings opt-in "Mark as read also completes Agent todos" is on. Mark read & done marks read and completes. FYI and Other offer Mark category as read for the listed messages, with Undo, and do not complete todos. Needs You has no Mark-all; select rows, then Mark selected as read or Complete selected. Done and Dismiss call `nativeAgent:home:todoUpdate` and stay on this computer. They do not archive, delete, mark read, or reply. The transcript and standing notes stay on that page. A refresh covers the Agent page with a light overlay and a spinner labeled Working…. The overlay does not cover the rail, so Mail, Calendar, and Brain stay reachable while that page loads.

A message is routed on the host. Naming a home skill runs that skill. "Triage inbox" (or "sort the inbox") runs triage. "Draft a reply" proposes a draft. A broad inventory question asks for unread, today, or a sender. A named filter returns host cards. A short follow-up pages the stored id list. Other questions still send the system prompt, recent turns, standing notes, and snippets from the cached inbox and calendar. That prompt must not invent mail and must not send. There is no sample mailbox to include. The transcript is `agent-chat.json` in the AI config directory. Standing notes are `agent-memory.json` in that same directory. Both survive a relaunch.

Triage still files recent inbox mail into Brain categories. Defaults are Needs You, Upcoming Today, Worth a look, FYI, and Other. Editing categories in Brain changes the next triage. Each row is a short summary, a category, and follow-ups (review a reply, open the message, or open an attachment). Those follow-ups are proposals. Drafts open in a compose window. Nothing is sent until you choose Send.

Needs an AI key, needs a mailbox, and an empty inbox cache are empty states. They do not show stand-in messages. Each triage row can open its message. Brief This Person uses the open message or a contact email from the panel. Run history is the local list of skill and triage runs, and choosing a row adds that saved run to the transcript.

## Profile

Email Brain is the leftmost rail entry after Calendar, with Profile, Categories, and Skills. It opens from that rail button and replaces the mail shell. Mail returns to folders, the message list, and the reader. Opening loads the cached persona, categories, and home and library skills, then calls `emailBrain:refresh` with source `open` (a fresh cache does not call the model).

Profile shows `ownerName`, `emailsAnalyzed`, `factsLearned`, and `updatedAt` when the cached persona includes them. Those counts sit in the profile summary card. Refresh and Rebuild are on that card, and the progress bar and status line sit with them. Recent updates from local activity stay with the sections. Writing rules are added, edited, and deleted on the profile. Learned rows (source `auto`) use Fix and Forget. Fix calls the model and replaces that stored row. Forget asks, then removes the row.

The summary card includes a collapsed Identity disclosure. After Refresh or Rebuild, it lists the Self graph stored on the persona: mailbox addresses with source `account`, then auto names, nicknames, and organizations. Account addresses come from the connected mailboxes after the model returns. Fix and Forget stay off those rows, and Forget leaves them in place. Auto rows use Fix and Forget. A nickname that comes back too short or too generic stays as it was. Identity rows are separate from `factsLearned`. `ownerName` on the summary is the same name as `identity.ownerName`. Before a distill has stored identity, the disclosure says Refresh learns names from your mail and that mailbox addresses show up after that distill. When Agent triage has an identity brief, its prompt weights Needs You toward a direct ask, a named responsibility, or a primary action on that owner. A missing identity leaves the triage prompt as it is today.

Refresh (`emailBrain:refresh` with source `manual`, and the hourly living refresh) is a soft distill. It rewrites the living generated persona from the mail sample plus the prior profile. Sent mail weighs voice, then inbox mail. Overlapping facts merge into one row. Newer sent mail wins when voice or facts change. Auto facts that are contradicted or clearly stale are dropped or rewritten. The model returns the full tightened persona, not a list of facts to append. When that pass includes rows, those rows replace the section. An empty section is not filled back from the old rows after a distill that produced other rows. If the model returns no section rows, the host keeps a prior section only when those rows are still useful, then dedupes and caps them. The host also dedupes near-duplicate labels and values and caps every section at 8 rows, the same cap already used when normalizing sections. User writing rules are not in the generated JSON and stay as written. Refresh does not replace the whole persona. Mailbox messages are not edited.

Rebuild asks, then calls `emailBrain:rebuild`. That is a hard distill: the generated persona is built again from a larger sent-and-inbox sample and replaces the previous generated profile. The prompt asks for 3 to 6 short tone rules and concise rows in communication-style, work-patterns, key-relationships, and decision-preferences. It does not invent facts that are not in the mail. The same 8-row cap and near-duplicate dedupe apply. User writing rules stay. Progress is the refresh and rebuild events. Rebuild and Fix call the model when a key is set. Rebuild needs a connected mailbox. No mailbox and an empty cache are host errors, not stand-in mail. A missing key tells you to open Morrow Mail → AI Setup.

Categories edit locally until Save, which replaces the stored list. That list is the taxonomy the next Agent triage uses. Add with AI and Fix category stay local until Save. They need an API key and show the host error when the key is missing. Use defaults copies the host defaults into the list, still unsaved until Save.

### Compose defaults and aliases

Settings → Compose also lists sender identities and recipient-visible name/address previews. Gmail `sendAs.displayName` supplies the default (a blank custom Gmail name inherits the primary Gmail name). Other primary addresses fall back to the account's sender name; a mailbox list label is separate. `brainCompose.accounts[id].senderNames` maps exact normalized email addresses to local Morrow-only overrides. An empty string intentionally sends address-only; deleting the key restores the default. Provider refresh never replaces this map or manual aliases. Removing an account cannot apply its id-scoped settings to a newly connected account. Discovery does not enumerate all Workspace domains or every possible plus address, and no Gmail setting or OAuth scope is changed.

Compose keeps a separate `fromDisplayName` snapshot alongside bare `fromAddress`. Both are included in dirty tracking, preview, draft save/resume, partial-delivery recovery and scheduled content. `messages.from_display_name` is nullable for legacy/provider drafts, whose original From header is parsed instead of applying current preferences. Existing legacy queued sends retain address-only behavior. Switching From explicitly resolves that identity's current default/override. The host rejects control characters and delegates MIME quoting and Unicode to Nodemailer. Display names never authorize an address, bypass alias verification, or trigger a fallback send. Bot `mail.send` uses the same defaults and keeps the first submitted name in its receipt; changing Settings cannot cause a matching request ID to submit again.

`messages.from_address` stores the bare sender address independently of the display label. IMAP envelopes and Gmail parsed headers supply it; local draft, Sent and recovered scheduled records preserve it. Draft hydration uses the host's bare `fromAddress`, so names such as `Operations <West>` cannot switch an alias to the primary account. Legacy rows use Nodemailer's header parser; an unresolved/ambiguous sender retains the draft instead of silently choosing primary. Adding equivalent legacy name metadata (NULL to empty, or a name already represented in the stored header) preserves an existing queued revision proof. A real name/content save still changes the proof and keeps newer work after delivery.

Legacy From cache text was built for display, with punctuation left unquoted. Revision compatibility therefore checks the complete historical name/address representation against newly parsed, separate provider metadata before trying RFC header parsing. It does not trim away quotes/angle brackets or guess an address from display text. The source text still participates in the revision proof, and real name, From and body edits remain protected.

Settings → **Compose** stores local preferences in `settings.json` under `brainCompose`. Email Brain Profile links to Settings → Compose and does not edit this form. No AI key is required. `emailBrain:getComposeSettings` reads `{ ccByDomain, bccByDomain, accounts }`. `emailBrain:saveComposeSettings` validates and replaces that object without changing other preferences. A missing `bccByDomain` is saved as `{}`. Domains are case insensitive, accept an optional leading `@`, and match exactly. A subdomain does not match. CC and BCC use the same line format, one domain per line. For example, `@example.com = colleague@example.com, team@example.org` on the CC list, and `@example.org = logs@example.org` on **Default BCC by domain**. Each domain can appear once on a list. A bad address is rejected, and the error names CC or BCC. Removing a line removes that domain's defaults. These settings survive persona refresh/rebuild.

Each account has an explicit alias list, an optional preferred From address for new mail, and an optional fallback CC domain for new mail. An alias line such as `ada@example.org = example.com` establishes that address as belonging to this mailbox and sets the domain used for BCC and for the signature. That domain is also the CC key, except on new mail when this domain has no CC rule and a fallback CC domain is set. The alias **does not rewrite From**. A bare alias uses its own domain. The preferred From field also registers that address as an explicit alias. Configure only addresses this mailbox may send from. A domain CC rule alone does not make every address at that domain your identity. The fallback domain selects only the CC list. BCC addresses and the signature use the alias domain when the alias sets one, and otherwise the host of From.

`mail:getComposeContext` takes `accountId`, optional `sourceMessageId`, `kind` (`new`, `reply`, `all`, `forward`), optional `fromAddress`, and optional `refresh`. The host verifies that the source belongs to the account and returns the selected From, received address, CC domain, policy domain, CC defaults, BCC defaults, own addresses, and From choices. Gmail's `users.settings.sendAs.list` uses an existing `gmail.settings.basic` grant (shared bundle, legacy settings grant, or primary full grant); it never opens consent. Only primary/accepted Gmail identities are discovered. The cache lasts ten minutes and is refreshed before sending an alias. Outlook and other SMTP accounts use explicit aliases: there is no inference of send-as permission from a Graph mail scope or a matching domain.

For replies, Reply All, and forwards, the resolver considers only exact addresses belonging to this mailbox: primary, Gmail-verified, or explicitly configured. Among owned aliases it checks `X-Original-To`, envelope evidence (`Envelope-To`, `X-Envelope-To`, `Received: … for`), `Delivered-To`, To, Cc, then Bcc. A non-primary alias wins over a primary Gmail delivery hop, so To `ada@example.com` plus Delivered-To `ada@example.org` selects `ada@example.com`. Multiple matching aliases use that header order, then wire order. With no recipient match, an owned original From (sent mail) is retained, otherwise the mailbox preference/provider default/primary is used and compose explains the fallback. Unmatched addresses never become From automatically. Older complete cached messages fetch their missing recipient evidence when opened; a failed fetch keeps the existing cached message available.

The domain used for the signature and for BCC is the alias domain when that alias address equals From and the alias domain is non-empty. Otherwise it is the host part of From. The CC domain starts from that same value. New mail can still use the account fallback CC domain when `ccByDomain` has no entry for that value. A missing kind is treated as new mail. An empty CC list is an entry and blocks the fallback. Reply, Reply All, and Forward keep the signature and BCC domain. They do not use the fallback. `mail.example.com` does not match `example.com`. BCC addresses come from `bccByDomain` for the signature domain. They do not follow the fallback CC domain. New mail uses the account's explicit preferred From, then Gmail's default send-as, then primary.

CC and BCC seed when a new composition opens, including replies, forwards, and AI reply suggestions. Reply All retains its other participants and excludes **all** known mailbox identities. Defaults are deduplicated case insensitively against To, Cc, Bcc, and the mailbox's own addresses. An address on both default lists is added to CC only. Before you edit a field, changing From rebuilds that field from its original text plus the new domain's defaults, so addresses added for the previous domain do not stay. Editing CC, including clearing it, stops automatic CC changes for that composition. Editing BCC, including clearing it, stops automatic BCC changes. The two fields lock separately. Resume draft and edit scheduled mail preserve saved From and recipients, including empty CC and empty BCC, even on From changes. Bot proposal review also preserves proposed recipients. Repaints, AI body changes, save, Send, and scheduling do not reapply defaults. You review the visible recipients and choose Send or Schedule.

The From picker is included in draft dirty tracking and its value passes through `mail:upsertDraft`, `mail:send`, and `mail:scheduleSend` to SMTP MIME From, saved draft From, and scheduled payloads. The host rejects addresses that are no longer configured instead of silently substituting primary. Gmail aliases must be verified in Gmail; a successful fresh discovery blocks removed/unverified aliases. When discovery is unavailable (including password-only Gmail), explicit aliases remain available with a warning, and the provider enforces send-as. Outlook needs mailbox/tenant alias support or Send As permission; Graph `Mail.Send` is not that permission and the current transport remains Outlook SMTP. Other SMTP servers may reject or rewrite any From other than their authenticated identity. There is no automatic retry with primary after a provider error.

## Inbox rules

Email Brain has a Rules tab, and Settings has an Inbox rules button that opens it. Gmail filters and Outlook inbox rules are created, edited, and deleted on the provider after `mail:grantRules`. Gmail uses `gmail.settings.basic` and label names from `gmail.labels`. Outlook uses `MailboxSettings.ReadWrite` and folder names from `Mail.Read`. An edit replaces the provider rule so the saved match and actions are the ones just reviewed. Rules that forward mail stay read-only here except for Delete. IMAP and password mailboxes store the rule locally and apply it only to Inbox mail downloaded after the rule was saved. Nothing is forwarded, and there is no sample mailbox.
