# Ingestion tuning and readiness: #520

Use a **32 ms cooperative work check** for runtime IMAP body ingestion, retaining the 24-message maximum, 256 KiB normalized text/HTML cap and commit-before-yield protocol. The initial 8 ms setting amplified small transactions. The wider setting mitigates that cost while preserving substantially shorter callback gaps in these synthetic runs. It does not promise a throughput improvement for every workload.

## Paired results

Elapsed values are medians of five complete update passes; callback values are the largest gap across all five passes. These are warm host-only updates to already-owned UIDs after warmup, not fresh provider downloads or first-sync throughput.

The selected 10k pass was 13.7% slower than baseline. The primary and opposite-order 100k comparisons were 8.9% and 8.0% faster; an earlier exploratory 100k pass was 9.4% slower. This variability, including ordinary background checkpoint work, prevents a universal speedup claim. In the primary pairs, 32 ms was 15% faster than 8 ms at 10k and 25% faster at 100k. The original separate 8 ms report retained its approximately 71% penalty; it is historical evidence, not the current setting.

The oversized-late scenario updates 30 ordinary messages and then one approximately 6 MiB normalized text/HTML message. At 100k, baseline/32 ms elapsed was 286.948/250.969 ms in the primary pair and 251.724/249.279 ms in the repeat. Their maximum gaps were 202.009/52.337 ms and 179.003/55.446 ms. A single message and its final commit remain indivisible.

## Root cause and choice

The primary 100k 96-message pass used a median 4 / 61 / 16 durable journal frames for baseline / 8 ms / 32 ms. Median SQLite COMMIT time was 15.137 / 108.826 / 36.548 ms. Median indexed-message stage time was 512.420 / 546.309 / 432.652 ms; journal append time and all other raw stage observations are retained below. SQLite commit time grows with transaction amplification; index/page-write/bookkeeping work and checkpoint overlap also vary. The data does not support attributing the whole penalty to journal fsync alone. Nested synchronous timings overlap and must not be summed; asynchronous checkpoint durations may begin outside the sample.

Exploration compared 8, 16, 24, 32 and 48 ms on the same checkpoints with the other caps unchanged. The 32 ms setting reduced physical transaction counts substantially and provided the best 100k elapsed balance in that sweep. Wider 48 ms slices raised callback gaps without a consistent throughput benefit. Smaller 16/24 ms slices offered shorter gaps but generally retained more transaction overhead. This is a measured engineering compromise for background host responsiveness, not a frame-time SLA.

Every yield still follows the existing journal append/hash/fsync and SQL commit. No transaction spans an await. Source/account/generation checks still run after each yield, and final resume state still follows all content batches. No result truncation, weakened flush/recovery, live parallel writer or acknowledgment before durability was introduced. Body metadata preparation and search rebuild keep their own 8 ms budgets.

## Method, provenance and limits

- Linux x64, Node v24.19.0, SQLite 3.53.2; Electron package 33.4.11 was recorded but never launched.
- Immutable runtime sources: baseline `e0ca1151e8fbf08929266463afbda6a382583786`, initial 8 ms `03b52fe331c4e2c2a6f7fb71fdf0f937c54f4dde`, selected 32 ms `aa2e14d56765f6428320d94551fbc536a6d467e4`. The integrated candidate has the same `host/mail/db.js` SHA-256 as the measured 32 ms source: `8eebf88984af5cc480e661a4340fe5d949e691452ecee4196f3b2e7de1319b86`.
- The final portable [benchmark harness](../../scripts/benchmark-residual-mail-work.js) SHA-256 is `08ef704d53b4567c6cbdba566169565333fa9549d48b9d08278fc8471b102b26`. All primary/repeat runs used that exact file. The exploratory harness source/hash and every raw result are archived in the [evidence JSON](2026-11-05-issue-520-tuning.json).
- Each count used one hash-validated checkpoint cloned independently per process, with a 95/5 two-account split and the same synthetic subject/sender/body distribution. Search/pending setup and opening/checkpointing finish before timing. Queries use two warmups, ingestion three, other writes one, then five samples. The 96 updated bodies each contain 1,000 distinct terms; this deliberately stresses index work.
- Primary order: baseline → 8 → 32 at 10k; 32 → 8 → baseline at 100k; then baseline → 32 for an independent opposite-order 100k repeat. The exploratory sweep ran ascending budgets at 10k and descending at 100k. Other local tests and fixture construction were stopped during all timed runs. OS/page caches remain warm; machine load, GC, storage and normal checkpoint scheduling can vary.
- Timer/prototype instrumentation adds diagnostic overhead and is identical within each primary pair.
- Ordinary automatic checkpoints remain enabled. Start/end flags and completion-stage observations show overlap in several passes, including baseline. Read those records before treating cross-run stage differences as an isolated operation cost. No timing threshold gates CI.
- The initial artificial 100k bulk seed hit the unchanged baseline checkpoint worker deadline. The 100k fixture was therefore created through production adapter transactions and the production header updater, then native SQLite backup of the quiescent committed working copy. Synthetic RFC IDs are restored before backup; delayed setup assignment avoids an unrelated local-copy matching scan. The 10k template used a production checkpoint. Both are hash-validated, immutable inputs; application checkpoint/deadline/durability code and timed update operations are unchanged. These results do not validate giant initial-journal replay or first-sync behavior.
- No real mail, credentials, live provider, AI or Electron window was used. Native macOS/Windows latency, packaged query plans, cold cache, first downloads, large-index creation, real disk behavior and power loss remain unmeasured. Individual normalization/SQL/index/journal/fsync calls may exceed the cooperative work/byte targets. Sampled RSS is not peak memory.
