## Method and reproducibility

Node v24.19.0, SQLite 3.53.2, linux x64. Electron package 33.4.11 is recorded for context; Electron was not launched. Harness SHA-256: `47285390fad7e9538d53e8badb379b891c280d3540e9576116667a6d425a1c6f`.

One 10,000-row and one 100,000-row complete-mail checkpoint were created with the baseline’s production adapter. Each has a 95/5 account split, one folder per account, 270-byte normalized text, common terms on every row, a rarer term on 1/97 rows, one small-account rare hit and tied timestamps every three messages. The harness adds a single large-account rare hit identically to each temporary copy before timing. Hash-validated source fixtures are copied, never modified. Opening/migration/checkpoint work finishes before measured scenarios.

The final runs were serial in this order: baseline 10k, candidate 10k, baseline 100k, candidate 100k, with local tests and fixture construction stopped. Each read has two warmups; writes have one. Five raw samples follow each warmup. Queries include bounded selectivity probes and metadata projection. A continuous setImmediate heartbeat measures the largest callback gap over every complete pass, including its final commit and a large body late in the pass. Warm OS/page caches and synthetic distribution limit generalization.

Pending selection has 0, 1 and 200 sparse incomplete bodies plus deep date/ID seeks. Maintenance flips 200 rows complete/incomplete in two durable transactions. Ingestion repeatedly changes 96 messages with 1,000 distinct body terms each; the oversized-late pass changes 30 ordinary messages and then one approximately 6 MiB text/HTML message. The stores grow beyond 100k during writes.

Reproduce with the commands in [PERFORMANCE.md](../PERFORMANCE.md#exact-search-and-pending-body-follow-up-520); use `--prepare-only --fixture-file PATH` to construct a reusable fixture without timing. Raw samples and full production SQL plans are in [the paired JSON](2026-11-05-issue-520.json). Bindings, mail content and identities are not diagnostic output.

## Interpretation

At 100k rows, the large-account single-hit query fell from 38.712 to 0.615 ms and empty pending selection from 34.576 to 0.132 ms. Common global search was essentially flat (427.309 to 416.939 ms); the small-account common query was slightly slower (38.864 to 40.920 ms), including the adaptive probe/grouping overhead. Broad exact ranking is still a material host delay.

For the 96-message ingestion pass, the maximum observed callback gap fell from 195.360 to 47.001 ms, while median total elapsed rose from 625.925 to 1,069.654 ms, about 71%. The oversized-late pass also took longer overall. More frequent durable commits and yields trade throughput for opportunities to serve other callbacks; journal/fsync acknowledgement is unchanged. These results support the practical query and cooperative-batching changes, with the remaining synchronous limits below.

## Plans, storage and setup

Production search plans include the complete outer query. Selective seeds use the covering term range, constrain remaining term groups through message IDs and fetch outer messages with `sqlite_autoindex_messages_1 (id=?)`. Small accounts can seed common terms; large accounts avoid walking their entire posting history. All groups retain complete per-term maximum weights and final ranking. The read-only reference and sort/To Me/Unicode tests verify results independently of these access choices.

Pending plans explicitly use `messages_pending_body_page`; deep keysets seek its date/ID tuple without sorting completed history. The partial predicate excludes complete, draft, local-only and retry-blocked rows. Retry deadlines, horizons and folder exclusions remain residual rules, so a large ineligible-by-time/folder backlog can still cost work.

RSS is sampled after operations across each process, not peak memory or retained-body accounting. No disk-I/O trace or native frame recording was collected.
