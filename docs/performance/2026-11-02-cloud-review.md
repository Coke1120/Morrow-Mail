**Morrow Mail — Cloud performance review and scoped fixes for `dev`**

Reviewed commit: [`6edf30f7ed51e69cc70c444bbc6f3b030c442244`](https://github.com/Coke1120/Morrow-Mail/commit/6edf30f7ed51e69cc70c444bbc6f3b030c442244), v0.3.16, merge-back #443. Review date: 2026-11-02 UTC. Isolated review checkout (branch `perf/cloud-review-responsive-attachments`): `/workspace/morrow-perf-review`. Evidence and reproducible probes: `/workspace/morrow-perf-artifacts/`.

The baseline review found substantial host-thread delays in ZIP creation and exact local search. This branch moves ZIP compression, CRC and assembly into a bounded worker and removes quadratic folder lookup work in retained sidebar refreshes. Local search remains the largest unresolved interactive delay in these fixtures. IMAP foreground priority also stops at a whole folder batch, and several history-sized queries remain despite bounded result pages. Recent performance fixes are present and materially improve ordinary lists, counts, body-cache retention and reconciliation fairness.

The authorized implementation is limited to F01 and F08, their regression tests and accompanying help/ADR. F01 is mitigated: compression no longer occupies the host thread, but large input cloning still pauses it. F02–F07 and F09–F10 remain open findings requiring separate query, protocol or data-ownership work. All mail, credentials, provider responses and benchmark data were synthetic. Providers were mocked; a preload blocked default fetch and remote sockets. No actual mailbox or credential store was read. No merge, approval, release or deployment was performed.

**Implemented changes and measured effect**

ZIP preparation admits one active worker, at most three active/queued jobs and at most 256 MiB of input, alongside the existing 64 MiB/file and 128 MiB/archive limits. Waiting jobs spawn no worker. Cancellation terminates the active worker; another starts only after confirmed exit. Inputs are cloned to preserve other consumers; output storage is transferred. Attachment writes are asynchronous and serialized, with identity/cancellation checks before their turn and after I/O. A write already started may finish after cancellation; files are not rolled back. The transfer panel exposes Creating ZIP and Waiting to save. The sidebar builds folder maps once per account snapshot while retaining nodes, badges and selection.

Three sequential runs per size, high-entropy input created outside timing, same Linux Node environment. Every candidate archive uses a fresh worker; the first 4 MiB sample includes module initialization. A 5 ms timer continued throughout compression; maximum gaps were approximately the submission/first-callback delays shown above. This improves responsiveness, not total compression speed. Input clone time and whole-process peak memory remain limitations; admitted input is not a peak-RSS cap. Native Electron packaging and frame timing still need target-device validation.

At 1,000 folders the retained renderer now copies 2,000 folder elements across two array constructions instead of 1,001,000 across 1,001 constructions; at 2,000 folders, 4,000 instead of 4,002,000. JSDOM warm medians fell from about 643 to 52 ms and 2,368 to 73 ms respectively (five samples, median of last four). These are diagnostic JSDOM measurements, not Chromium frame times.

Actual handler fixtures cover cancellation/account removal/message identity changes after worker preparation, cancellation while writing, serialized same-path saves, waiting-save cancellation and write-failure recovery. The actual renderer/Features DOM checks retained nodes, live badges/selection, linear lookup work and updated help. The check is part of `npm run check`. **Measurement method and limits**

Environment: Codex Cloud Linux x86_64, kernel 6.18.57, KVM, Intel Xeon Platinum 8573C, 5 visible vCPUs, approximately 18,007 MiB RAM, overlay filesystem for `/workspace`, no swap. Node **24.19.0**, better-sqlite3 **12.11.1**, SQLite **3.53.2**, jsdom **26.1.0**. Electron was not launched. This is **not a macOS Electron/APFS or Windows/NTFS benchmark**, and shared VM timings are not target-device guarantees.

The database fixtures contain 10k and 100k messages in one account/Inbox, with current production schema/triggers/indexes, complete synthetic bodies, approximately 22 search postings per message, 20% unread and 5% starred. The last 1,000 rows share a thread. The files are approximately 56.3 MiB and 571.5 MiB. Fixtures were initially created through the production DB API, then populated directly with synthetic SQL for practical setup time; direct seeding is outside timings. Durability settings were relaxed only on that seed connection. Measured production opens/writes use the unmodified adapter, transactions, journal and fsync. These fixtures exercise scaling rather than the complete distribution of real mail.

Queries run five times serially. “First” is the first query invocation on an already-open synthetic store. “Warm median” is the median of runs 2–5. Startup runs three times with fresh working copies; these are warm filesystem-cache opens, not power-on cold starts. ZIP/body/Gmail probes run three times, with input construction outside timing and main-isolate GC between samples. First and later values remain in JSON. Synthetic provider scheduling runs three times per profile. Sidebar runs five retained renders. Recipient RSS is one exploratory run; main-isolate GC does not establish retained worker heap.

For synchronous calls, a queued `setImmediate` measures how long another callback waits. Startup also samples a 5 ms timer and records phase boundaries. For asynchronous reconciliation, the first callback delay only proves that the first yield occurred; it is not a measurement of the maximum gap over the entire pass. JSON byte counts below estimate payload scale, not actual Electron structured-clone time or wire size. No cold disk-cache eviction, native frame timing, real API throughput or native keychain performance was measured.

**Detailed findings**

1. **F01 — P1: ZIP creation blocks host IPC for the whole archive.**

   Caller chain: `renderer/app.js::saveAttachmentsZip` → `startAttachmentTask("mail:downloadAttachmentsZip")` → `host/main.js` IPC registration → `host/ipc.js::liveAnswer` → `engine.answer` → `attachmentOperation` → `zipFiles`. The handler calls ZIP construction after the awaited transfers, then calls `fs.writeFileSync`. ZIP construction itself uses `deflateRawSync`, a JavaScript CRC loop, per-file buffer concatenation and final archive concatenation. There is no yield or cancellation checkpoint inside that CPU section. See [renderer entry](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/renderer/app.js#L8033), [handler](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/engine.js#L3063-L3075), and [compression/checksum](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/zip-bytes.js#L73-L101).

   Measured with high-entropy synthetic bytes, representative of already-compressed attachments: 4 MiB took 105–113 ms, 16 MiB 405–445 ms, 64 MiB 1.68–1.71 s, and two 64 MiB files 3.35–3.55 s. The next callback waited for effectively the same duration. These sizes are within the application's 64 MiB/file and 128 MiB combined limits. The benchmark calls the actual ZIP function; network, dialog, disk-write time and UI IPC overhead are excluded, so it isolates a sufficient blocking component rather than claiming end-to-end save latency. Current download concurrency and cancellation tests pass; they do not bound this final synchronous stage.

   Remedy: move compression/checksum/archive assembly to a worker or a bounded streaming implementation and write asynchronously. Retain exact selection, names, bytes, cancellation ownership and safe completion semantics; prefer streaming or transferred buffer ownership over extra whole-file copies. Regression: save 16/64/128 MiB compressible and incompressible fixtures while issuing a heartbeat/list request; cancel during compression and before publication; verify ZIP CRC/content, duplicate filenames, failure cleanup and concurrent consumers. Preserve existing transfer limits.

2. **F02 — P1: local search can occupy the host for nearly a second; #434's selective probe does not constrain the outer join.**

   Caller chain: toolbar search / `loadList` → `mail:searchLocal` → `engine.searchLocal` → `db.searchMessages` → synchronous adapter `stmt.all()`. Each term groups all matching postings, joins the term results, then performs complete weighted/date/id ranking before `LIMIT 100`. Returning 100 metadata rows bounds IPC, not the ranking work. See [renderer call](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/renderer/app.js#L9350), [engine projection](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/engine.js#L2579-L2586), [query construction](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/db.js#L1192-L1221), and [synchronous materialization](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/persistence.js#L109-L122).

   At 100k rows, common two-term search took 397 ms warm unscoped and 949 ms scoped to the account containing that history. Captured plans show per-token grouping and temporary ranking, with the broad scoped path probing each account message's postings. Additionally, the rare `subject` term has one result: its scoped aggregate correctly uses the term-range index, but the **outer** query still uses `SEARCH m USING INDEX messages_thread (account_id=?)`. It took about 59 ms; the unscoped one-result plan instead scans the tiny aggregate and probes `m.id`, about 1.1 ms in a separate plan probe. That latter comparison is one sample, not the five-run table. Thus #434's rare-term improvement is real inside the aggregate, but not a guarantee for the complete plan. Existing tests assert the inner term-index path without prohibiting the outer account scan.

   Remedy: retain exact ranking and AND/prefix semantics; move query ownership to an isolated read worker with a coherent snapshot and request cancellation. Separately make selective outer joins candidate-driven, verified against SQLite plans and skewed multi-account distributions. Do not truncate candidates to an arbitrary first N. Regression: 100k+ common-prefix/multi-term queries, a single matching result in a large account, duplicate timestamps, disconnected accounts, accents, AND semantics and rank parity; verify both inner and outer access paths and that stale searches cannot hold up a new search/list request. ADR #438 already defers broad exact-search work; this report confirms that residual and adds the outer selective-join case.

3. **F03 — P2: IMAP foreground priority is delayed by the whole current bootstrap batch.**

   Caller chain: 45-second background tick → `syncAllAdmitted` → `syncAccountAdmitted` → account `exclusive` lane → `syncFolderPolicy` → `bootstrapFolder` → `remote.fetchMessages` → parse all returned messages → local commit/reconciliation. A new uncached open reaches `ensureBody` → the same lane. Priority is checked between folder operations, but `fetchMessages` collects the entire batch before the lane can release. The source caps the batch at 100 for ordinary IMAP and 50 for Outlook; warm refresh starts at 20. See [priority lane](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/engine.js#L158-L214), [bootstrap await](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/engine.js#L945-L1002), [batch collection](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/remote.js#L477-L496), and [lane ownership around folder walk](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/engine.js#L1229-L1289).

   A deterministic full-engine probe uses the real `remote.fetchMessages`/parser and a synthetic async generator delayed 25 ms per background message. A foreground open submitted as the first background fetch begins starts its provider fetch only after **100/100** ordinary-IMAP or **50/50** Outlook messages. Across three runs: 2.63–2.68 s and 1.32–1.33 s open completion. This is simulated backpressure, not a measurement of actual IMAP throughput or a per-message network round trip. Cached complete opens still avoid this lane. Gmail has a separate per-read stop check and must not be described as having the same 100-message problem.

   Remedy: smaller adaptive sub-batches or a transport design that finishes/drains the active IMAP command safely and yields account ownership at bounded checkpoints. Do not interrupt an IMAP iterator unsafely or advance the durable UID cursor past uncommitted messages. Regression: a slow stream, pending open/flag action after the first result, correct UID cursor after partial progress, cancellation/reconnect and remaining-folder fairness. Include Outlook's 50-row path, not only Gmail's per-read budget.

4. **F04 — P2: an overnight SQL page can still inspect the full completed-mail history.**

   Caller chain: background poll → `syncAllAdmitted` → `fillOvernightBodies` → `nextOvernightRow` → `selectMessages({needsBody:true,limit:200})`. #420 bounds the JS loop to two returned pages; #426 retains unfinished cursors across day/night windows. Both are present. The `needsBody` predicate, however, is not covered by a matching pending-body ordered index. In this production SQLite fixture the plan uses `recipient_headers_page (is_draft=?)`, checks body status across non-drafts, and uses a temporary B-tree for sort. See [two-page selector](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/engine.js#L2258-L2279), [eligibility predicates](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/db.js#L1702-L1721), and [query execution](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/db.js#L1786-L1818).

   With 100k complete messages and **zero** candidates the query still blocks for approximately 59 ms warm; one oldest pending message costs the same. At 10k it is approximately 5 ms. Empty/end-of-history resets the cursor, so eligible overnight polls can repeat this work. The exact chosen index may change with statistics or packaged SQLite; the absence of a candidate-oriented bound remains. Existing mocked selector tests prove two DB calls/400 returned headers, not a bound on rows SQLite visits. This is not a re-report of the fixed unbounded JS page loop.

   Remedy: a measured partial pending-body index/backlog structure ordered for this keyset, with retry timestamps, identity changes, folder exclusions and horizon semantics retained. Keep the JS two-page budget and cross-window cursor behavior. Regression: real SQLite with 100k complete rows plus 0/1/200 sparse pending rows, future retries, blocked bodies, excluded folders and deep keysets; assert candidate-driven plans/work as well as result count, and include all-complete idle polls.

5. **F05 — P2: runtime body commits can exceed the responsiveness budget despite bounded row counts.**

   Caller chains: IMAP sync → `applyFolderSyncAsync` → up to 24 body-bearing rows inside `applyFolderSync`; foreground/visible/overnight fill → `ensureBody` → `updateMessage`; Gmail adoption → `applyGmailMessage`. These reach synchronous indexing, SQL writes and durable journal serialization/write/fsync. `updateChanged` also binds new values in its change predicate, so large strings can occur more than once in serialized commands. The 8 ms startup metadata budget from #433 does not apply to this runtime loop. See [24-row runtime batch](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/db.js#L1404-L1453), [index body extraction](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/db.js#L936-L1023), [changed-value binding](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/db.js#L163-L170), and [journal encoding/fsync](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/persistence.js#L218-L238).

   Actual production calls: 24 normalized rows containing **94,500 bytes (92.3 KiB) in each text/HTML field**, approximately 4.33 MiB total body strings, take 90–94 ms; the first other callback waits 90–94 ms. This models HTML plus derived text, not 24 raw sources with twice the source limit. A single update with approximately 3 MiB in each field (6 MiB normalized content, not 3 MiB on the wire) takes 82–143 ms. A complete cached open of that large body takes 27–28 ms before IPC/renderer sanitization. Plain-body squashing applies a regex to the entire string before taking the 200k-character search slice. Existing batch tests show eventual yielding, not a per-turn time or byte bound. Original probe log's “88 KiB” label was imprecise; the actual generated string is 94,500 bytes and is reported here accurately.

   Remedy: apply elapsed-time and byte budgets to runtime batches, keeping yields outside committed transactions. Move expensive parsing/normalization/index preparation off the host where possible. For a strict bound on a single huge write, use an explicit database-owner design or review body layout separately; merely lowering 24 cannot bound one statement/fsync. Preserve journal-before-ack and crash/replay semantics. Regression: large HTML/plaintext/inline-image bodies, one oversized operation, repeated 24-row batches, foreground heartbeats, indexed-content parity, crash/replay, rollback and disk-full failure. Do not trade durability for a faster benchmark.

6. **F06 — P2: startup migration and warm verification still contain long synchronous regions.**

   Caller chain: `main` startup → `initMail` → `db.openDatabase` → `startupPhase(..., transaction(migrate))` → `CREATE INDEX`; later `ensureSearchIndex` → count plus missing/orphan document checks before admission. The phase wrapper yields **before** migration, not during an index build. See [opening sequence](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/db.js#L524-L556), [list indexes](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/db.js#L415-L419), and [warm verification](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/db.js#L1057-L1085).

   Three independent copies of the 100k fixture with four list indexes removed take 285–289 ms in `startup.migrate`; maximum observed 5 ms timer gaps are 401–425 ms, including adjacent opening/fsync work. This is a deliberately missing-index upgrade fixture, not a claim that every version upgrade drops those four indexes. A current-schema reopen still takes approximately 52–54 ms in search verification. Current warm-cache admission is approximately 399–439 ms total; opening performs a fresh whole-file `.live` copy, taking roughly 179–223 ms for this 571.5 MiB store. Copy is asynchronous and must not itself be labeled a main-thread CPU freeze. A warm-start timer gap of 115–125 ms was observed elsewhere in opening, but was not isolated to a single native call.

   Remedy: separately design exclusive migration/query-worker ownership, and a bounded verifier preserving all three index-consistency structures, admission, durable markers and restart recovery. Working-copy reuse needs its own recovery protocol; do not simply trust/delete the `.live` file. Regression: actual large missing-index stores, phase heartbeats, cancel/close/crash/restart, corrupt/orphan entries and admission checks. Existing #433 startup tests correctly cover the 8 ms metadata budget and recovery with 300 rows; they do not establish a migration latency ceiling. #438's ADR explicitly deferred these ownership/verification changes.

7. **F07 — P2: large Gmail attachment decoding has an additional host-thread CPU/memory spike.**

   Caller chain: Preview/Open/Save → `attachmentParts` → Gmail `readPart`/session attachment → API `attachment` → response text + `JSON.parse` → base64url validation/decode/re-encode. Returning bytes then passes through immutable cache/consumer copies; preview additionally crosses IPC. The limits bound file size and concurrent groups, not per-turn CPU or peak copies. See [Gmail response parse](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/gmail-mail-api.js#L80-L114), [decoder](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/gmail-mail-api.js#L14-L19), and [cache copies](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/attachment-cache.js#L32-L44).

   With a mocked already-available response string, a 16 MiB decoded attachment takes 69–81 ms and 32 MiB takes 151–156 ms; the pending callback waits 154–159 ms at 32 MiB. No network/download duration is included. This is distinct from ZIP compression and also affects single-file previews. RSS deltas vary with buffer reuse/GC and are not a measured heap ceiling. Per-file admission, 64 MiB completed-cache budget, 16 pending entries and two active groups all remain useful protections.

   Remedy: worker decode/validation or a bounded streaming pipeline, response-size admission while reading, and explicit transferable/immutable buffer ownership. Preserve canonical base64 validation, per-consumer cancellation and account/message identity rechecks. Regression: 16/32 MiB payloads, malformed/canonical base64, abort during body/decode, simultaneous preview and save, and heartbeat/memory assertions appropriate to the test runner.

8. **F08 — P3: retained sidebar updates still allocate and search folder arrays quadratically.**

   Caller chain: background `emitAccounts` → `mail:accountsUpdated` → `onAccountsUpdated` → `renderAccounts`. Its retained-tree branch calls `foldersOf(account).find(...)` once per visible folder; `foldersOf` creates a new concatenated array each time. See [event handler](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/renderer/app.js#L11588-L11596), [retained branch](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/renderer/app.js#L4643-L4658), and [array construction](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/renderer/app.js#L442-L445).

   Production renderer functions on synthetic JSDOM retained the same nodes, but copied 40,200 / 1,001,000 / 4,002,000 folder elements per render at 200 / 1,000 / 2,000 folders. JSDOM warm render medians were about 44 / 643 / 2,368 ms; those are **not Chromium frame timings**. The deterministic quadratic work is the evidence for this finding, with native impact still to profile. Remedy: construct per-account folder maps once per snapshot and update only changed badge/selection nodes. Regression: retained node identity, unchanged-refresh DOM mutation count, and linear lookup/allocation counts at 1k+ folders. This is the already-deferred G14 residual, not a claim that the tree is rebuilt on every status event.

9. **F09 — P3: recipient worker memory grows with historical messages, not just unique recipients.**

   Caller chain: compose suggestion → `mail:suggestRecipients` → `recipient-suggest.list/refresh` → paged header messages to worker → `copies`, `messages`, and per-address `sightings` maps. Moving this off-thread and using header deltas correctly avoids a repeated host scan on body/flag changes, but per-message history is retained for the worker's lifetime. See [refresh](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/recipient-suggest.js#L42-L85) and [worker retention](https://github.com/Coke1120/Morrow-Mail/blob/6edf30f7ed51e69cc70c444bbc6f3b030c442244/host/mail/recipient-suggest-worker.js#L4-L44).

   One 100k-message run with very few unique addresses raised process RSS from about 54.6 to 273.2 MiB, approximately +219 MiB, after the first build/response/main GC (~1.09 s); warm query was 0.59 ms. This does not isolate retained worker heap from SQLite caches/transient allocations and does not demonstrate a leak. The unbounded history maps are static evidence. Remedy: persistent incremental address aggregates or compact per-message contribution records, preserving Gmail-copy dedup, frequency/recency ranking, removal and name precedence.
