# Gmail API migration and least privilege

Status: implementation in **draft PR #305 → dev**, pending review and release. This describes the draft source, not released v0.2.38. No user mailbox, live OAuth grant, Google Console setting or public policy was changed during implementation.

## User behavior and scopes

Continue with Google remains OAuth. New Google mail connections use Gmail API. Existing Google OAuth IMAP accounts keep their current connection until Settings → Accounts → **Migrate Gmail to Gmail API** is reviewed and confirmed. Generic reconnect directs legacy accounts to that review rather than silently replacing their mail token. Account id, cached mail, signatures, scheduled payloads and local drafts stay; there is no delete/recreate step. Password/app-password and Microsoft accounts retain their transports. A deliberate password reconnect explicitly returns mail to IMAP/SMTP.

Mail requests `openid email https://www.googleapis.com/auth/gmail.modify https://www.googleapis.com/auth/gmail.settings.basic`. `gmail.modify` covers messages/bodies/attachments, drafts, send/reply, labels, flags, Trash and restore. `gmail.settings.basic` covers send-as identity enumeration, vacation and filters. Full-mail `https://mail.google.com/`, redundant `gmail.labels`/send/compose, Contacts and Drive are not requested. Optional Google Calendar separately requests `openid email https://www.googleapis.com/auth/calendar.calendarlist.readonly https://www.googleapis.com/auth/calendar.events`; mail consent does not imply Calendar consent. Microsoft retains Outlook-only mail plus its separate Graph bundle.

Settings shows the requested mail/Calendar scopes and the actual scopes on saved credentials, including an older broad token kept for Calendar. Google authorization uses `include_granted_scopes=false`; this does **not** revoke existing grants or guarantee a narrower returned token. A returned full-mail grant is recorded and warned about. To deliberately retire broad access, review Morrow in Google Account connections, revoke there, then explicitly reauthorize mail and Calendar separately. That may interrupt other saved Morrow Google grants; local work remains. This app does not change Console registration or revoke access automatically. `gmail.modify` remains restricted; narrower scope requests do not establish that verification or CASA disappears. Google decides from the real app/data flow.

## Coverage in source

| Feature | Gmail API path and cache behavior |
|---|---|
| Folders / labels | Lists actual labels and a derived All Mail view; stable label ids survive rename, hierarchy renames reuse existing label APIs. Removed labels retain unbound cached folders. System Sent/Drafts cannot be arbitrary move destinations: use Send / Save draft. Sent membership is retained when adding a user label; drafts cannot take arbitrary labels. Undo to original Sent/Drafts relies on confirmed untrash membership, never a manual protected label. |
| Sync / backfill | Bounded `messages.list` pages, persisted page/history cursors, first-page refresh during backfill, history changes/deletions, expired-cursor rescan plus bounded known-copy verification. Respects history horizon and preserves older local cache. History/polling replaces IMAP IDLE. |
| Cache identity | Provider message/thread/draft ids are stored separately. Numeric local surrogate ids are never conversions of Gmail ids. Verified unique RFC Message-ID matches bind all legacy label copies, including copies outside the current live labels, before pruning obsolete memberships; old folder/UID/UIDVALIDITY aliases are recorded. Multiple provider matches or ambiguous same-folder legacy copies fail without partial binding. Unrelated messages and pending local edits are retained. Local message/thread ids and complete bodies stay. |
| Bodies / attachments | Gmail MIME parts normalize encoded headers, text charsets, plain/HTML and inline images. Large text parts load for full-body reads; ordinary attachment files stay on demand. Gmail attachment ids are namespaced. Opening a complete cached legacy message refreshes its attachment metadata independently of body completeness, retaining correct cached text/HTML and reusing fresh metadata on repeated opens. A read-only unique identity lookup can recover metadata even after the message's folder membership changed; write membership guards remain. Stale IMAP selections fail rather than addressing a different Gmail part. Open/save/ZIP reuse existing byte paths. API MIME/base64 response limits fail explicitly. |
| Read/star, search | Modify UNREAD/STARRED labels. Text/sender provider search uses provider ids and real folder memberships, avoiding unbound IMAP search identities. Cached search remains local. |
| Drafts | Explicit Save builds MIME, preserving Bcc, reply headers and attachments. New revision is committed locally first; a confirmed replacement is uploaded before the verified prior server copy is moved to Trash. Pending legacy edits keep their content and detach unverifiable old UIDs. Saving an as-yet-unmapped legacy draft also detaches its old UID before changing the local RFC identity, creates a fresh server draft and warns that the unverifiable earlier copy remains. Repeated Save and discard then use the new confirmed identity. Remote discard failure retains the local draft. Saving never sends. |
| Send / scheduled send | Gmail `messages.send` from the existing reviewed Send / authorized bridge / due-schedule pipeline. Actual MIME includes Bcc for Gmail's delivery envelope and reply headers. Provider acceptance is durably handled before best-effort local filing. Returned message ids bind Sent rows directly. Ambiguous writes are not automatically retried, including lost send acknowledgements. No SMTP fallback. |
| Aliases / settings | Existing Gmail send-as checks, provider labels, vacation and filters remain API operations with their complete permission gates. No new forwarding or permanent-delete capability. |

Every migrated remote mail path dispatches through `gmail-session.js` in `remote.js`; an attempt to create an IMAP client for a migrated account fails. The account-generation and current-credential checks reject stale responses after removal/reconnection. Microsoft and generic IMAP/SMTP paths remain separate.

## Trash semantics and Undo

Before this change, ordinary Delete already moved to Trash. Actual permanent behavior existed in batch Delete **from Trash** and IMAP draft cleanup; no Gmail HTTP `messages.delete`, `threads.delete` or `messages.batchDelete` path was found. This draft therefore does not claim to remove a bypass-Trash Inbox button.

Gmail Delete/thread Trash/batch Delete use Trash. Deleting again while in Trash stays there. Persisted old Gmail permanent intents are refused before credentials/provider writes. Mixed-provider batches apply policy by account; Microsoft/other IMAP deletion-from-Trash and cleanup behavior remain unchanged. All Gmail `removeUid` paths, including legacy IMAP draft replacement/discard/post-send cleanup, move to the actual Trash folder and never invoke IMAP messageDelete/expunge. Missing Trash fails closed.

The existing journal offers Undo only after a confirmed move. Structural actions deduplicate label/All Mail cache copies by Gmail provider identity; legacy RFC candidates are still checked for a unique provider match before a write. Each confirmed Trash/Archive journal operation retains its own immutable provider-membership snapshot. Repeated Trash cannot overwrite it. Trash hides cached copies from ordinary labels/All Mail; Undo restores their memberships while preserving later read/star/new labels. Archive removes INBOX regardless of the displayed cache folder, including All Mail/search copies; its Undo restores prior Inbox membership. Uncertain writes stay unknown and need review; the app does not automatically retry them. Gmail's own Trash retention still applies: Trash is not a guarantee of indefinite retention or immediate erasure. Old remote draft revisions now remain in Trash rather than being expunged.

## Reauthorization, concurrency and recovery

Migration requires an explicit matching OAuth account, affirmed review and sufficient mail permissions. Unresolved mail actions and a currently sending scheduled delivery block the switch. The OAuth result pins the mailbox incarnation and prior credential; cancellation, mismatched account, removal, changed credentials or reported credential/SQL failure preserve the previous usable connection. Cancellation is checked again inside the account queue before commit. UI serializes mail and Calendar authorization; an unconfirmed cancellation keeps another authorization blocked. A confirmed cancellation retires late results. An authorization already committed before Cancel is retained and can be reviewed by refreshing permissions.

New credentials are validated and saved with compensation around a synchronous SQLite transaction that switches the account transport. Omitted existing feature grants are preserved in their own slots. Calendar reauthorization validates both Calendar-list and event permissions before replacing Calendar credentials; a mail-only or incomplete Calendar token leaves the working credential untouched. It does not replace primary mail credentials. Actual token scope strings are not combined across tokens. Refresh uses received scopes, not an expanded request. Credential storage and the SQL journal are separate stores: reported failures are compensated, but process/power-loss atomicity across both stores is not claimed. Storage uncertainty requires reconnect/review, not automatic data migration or resubmission.

## Validation and review gates

Fixtures use synthetic accounts/tokens/provider responses and temporary databases. `check-gmail-mail-api.js` tests primitive paging/MIME/drafts/explicit sends, HTTP/cancel/ambiguous-write handling and real Gmail-vs-other-provider deletion paths. `check-gmail-cache.js` tests production cache/session SQL, identity adoption/refusal, resumable history/backfill, lazy bodies/attachments, rename/Trash/restore and removal races. With installed CI dependencies it uses production SQLite/parser; the permitted local VM uses Node SQLite and a header-parser fixture, which does not certify native persistence/parser behavior. `check-gmail-engine.js` runs the actual engine, remote adapter, MIME composer, action journal and production SQLite in CI, with synthetic OAuth and sockets forbidden. The UI fixture exercises actual renderer functions in synthetic DOM/VM; this is not rendered/native validation. Existing OAuth/Calendar and other-provider suites remain part of the full repository check.

Record exact-head CI/test results in the PR. Native macOS/Windows rendering and key storage, large-account performance, provider registration, real grant narrowing/refresh/Calendar coexistence, real MIME delivery/alias behavior and a Google-facing demo remain unverified. Prior blocked browser file navigation (`ERR_BLOCKED_BY_ADMINISTRATOR`) and daemon access (`Permission denied`) were not retried or bypassed. No native/rendered claim is made from unit VM results.
