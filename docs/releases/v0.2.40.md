## Attachment transfers

This release includes the attachment improvements merged in PR #310 and promoted in #311. They were not in the published v0.2.39 artifacts. Preview, Open and Save share an in-flight read for the same current attachment, and can reuse a complete result from a bounded process-memory cache. There is no measured live-provider speed claim: reuse avoids duplicate reads only while the same bytes remain valid and retained.

Save and Save as ZIP show the system save picker before fetching. Cancelling that picker starts no provider read. The Attachment transfers panel shows request-specific phases and received bytes when available, with individual Cancel controls. It does not hold the shell-wide busy flag or show a fabricated percentage.

Closing Preview or cancelling one consumer detaches that consumer; another Save or Open using the same read continues. The last consumer cancels queued or active provider work. A system picker may need to be closed separately. Cancellation cannot recall an already completed disk write or application launch. A crash during the final file write can still leave a partial file at the chosen path; this release does not claim atomic writes.

## Bounds and exclusions

- The cache retains complete files only: at most 32 MiB per retained file, 64 MiB total, 64 entries, and a five-minute TTL with LRU eviction. It is process memory, cleared when Morrow exits; there is no persisted attachment cache or background attachment prefetch. Larger permitted downloads remain on demand without retention.
- Incoming reads are bounded at 64 MiB per file and 128 MiB combined for a ZIP. Gmail keeps its existing response bounds, so a provider can impose a lower effective limit. Outgoing attachment limits are unchanged.
- Two batches can be active with at most 16 pending files. Large ZIP selections are processed in bounded eight-file batches; the pending-file bound does not truncate a 17-file selection.
- Cache hits recheck the current account, message and attachment identity. Account removal, reconnect or migration invalidates retained bytes and pending reads. Failed, incomplete and cancelled reads are not cached; each consumer receives its own copy.
- Exact attachment selections, legacy Gmail identity recovery, IMAP UIDVALIDITY checks and local draft files remain supported. Bot access remains metadata only. Connection pooling, background body scheduling, IMAP chunk tuning and PDF worker changes are outside this release.

Features → Attachments, the reader transfer controls and the UI/help docs were updated together in #310. Their existing offline DOM/transport checks remain part of the full check suite; this version change adds matching What's new and release notes without changing the transfer implementation. See the [attachment decision and limits](../adr/2026-10-26-attachment-transfers.md).

## Validation and distribution limits

Synthetic tests cover bounded cache/TTL/LRU behavior, shared IMAP/Gmail reads, identity checks on warm hits, Save-before-fetch, per-consumer cancellation, interrupted/repeated UI actions, a 17-file ZIP and request-specific renderer progress. They use fake accounts/providers and temporary data. The approved attachment source at `6a4f7614d074ace2481013afc45e5d4e7f4869e9` passed exact-head CI run 40287880798 and a bounded independent functional review. This release preparation does not claim live throughput, native rendering, system-dialog behavior or real external-application launch verification.

Windows remains unsigned. macOS uses ad hoc signing without Apple Developer ID or notarization. The separate Ed25519 update manifest authenticates the macOS download; it does not grant OS execution trust. Native updater transitions remain unverified. No app was installed or executed, live mailbox accessed or OAuth grant created for this preparation. The prior browser denial was not retried or bypassed.

The [v0.2.39 Gmail migration and AI data-permission behavior and rollout prerequisites](v0.2.39.md) remain applicable: existing Gmail accounts need the reviewed migration/reauthorization action, requested narrower scopes do not revoke old broad grants, Calendar uses a separate grant, and Google Console/API enablement and verification status are separate owner work. This attachment release changes none of those settings or the external policy website and does not certify live Google readiness.
