## Gmail API migration

New Google mail connections use Gmail API. Existing Google OAuth IMAP accounts keep their current connection until **Settings → Accounts → Migrate Gmail to Gmail API** is reviewed and confirmed. Migration retains account identity, cached mail and local drafts; pending or uncertain actions can block the switch. Migrated Gmail uses history/polling with no IMAP/SMTP fallback. Microsoft and other IMAP transports are unchanged.

Mail requests `openid email https://www.googleapis.com/auth/gmail.modify https://www.googleapis.com/auth/gmail.settings.basic`. Optional Calendar separately requests `openid email https://www.googleapis.com/auth/calendar.calendarlist.readonly https://www.googleapis.com/auth/calendar.events`. Mail consent does not imply Calendar consent or remote-AI permission.

**Old broad Google grants are not automatically revoked.** A narrower request is not proof that the received grant became narrower. Accounts distinguishes requested and saved granted scopes, including old broad credentials retained for Calendar. Deliberately retiring broad access requires review in Google Account connections and explicit reauthorization of mail and Calendar; revocation there can interrupt other saved Morrow grants. Migration does not perform Google-side revocation or delete/recreate the account.

Gmail Delete, thread/batch Trash and old remote draft cleanup retain Trash. Repeating Delete from Trash does not permanently erase Gmail mail; persisted permanent Gmail intents are refused. Gmail's own Trash retention remains applicable. Undo requires a confirmed operation and preserves its original membership snapshot and later flags; uncertain writes are not retried automatically.

## Google project and rollout prerequisites

The **Gmail API must be enabled in the Cloud project for the Desktop OAuth client used by the packaged app**. Calendar functionality additionally needs the Calendar API enabled in that project. These requirements are confirmed in Google's [Gmail setup guide](https://developers.google.com/workspace/gmail/api/quickstart/nodejs) and [Calendar setup guide](https://developers.google.com/workspace/calendar/api/quickstart/nodejs), checked 2026-10-26. This release does not create a client, enable an API, change Console settings or obtain a live grant.

The project owner must review the actual Branding/Audience/Data Access configuration, Desktop client/platform setup, authorized policy/domain information and the two requested scope sets. Keep legacy full-mail declarations while supported legacy accounts still need them; do not remove declarations merely because the new request is narrower. See [OAuth configuration and its Testing/verification gate](../OAUTH.md#hard-blocker-testing-and-verification).

`gmail.modify` remains a restricted scope; narrower requests do not establish that Google verification or CASA is unnecessary. Testing/verification restrictions remain blockers for affected Google sign-ins: a Testing project is limited to its permitted test users, and refresh restrictions still apply. **The real project's API enablement, audience, verification/assessment and rollout status were not inspected or certified by this release.** A published app artifact is not evidence of general Google production availability. Missing provider permissions/configuration must be resolved through the project/account review, not bypassed by the app.

The external policy website was not modified. Its previously confirmed v0.2.38 baseline is not evidence that the new Gmail/AI consent disclosures or Google's requirements are fully aligned. Released-version policy/terms alignment, actual Console evidence and Google's determination remain separate owner work.

## AI data permission (#302)

Settings → AI and AI Setup disclose the saved destination/model/account, data categories, purpose, local/remote distinction and revocation limits before an affirmative choice. Existing API/ChatGPT configurations start with AI data use off. Saving credentials, signing in and model catalog reads are not consent. Background processing needs a separate opt-in. Destination/model/account changes retire permission; Cancel / revoke stops queued and active requests, but cannot recall delivered data. User consent is not a provider-retention, training or Google compliance certification.
